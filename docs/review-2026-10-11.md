## 1. `split.ts`: a nested `recv` after a `let` in a clause body is rejected

### Symptom

A `recv` in tail position of a clause body is allowed by D167, and works
when the clause body has no `let`. With a `let` before it, and anything
after the outer `recv`, the compiler rejects the program with a message
about a `do` the program doesn't contain, positioned at the outer `recv`:

```lisp
(defun worker (c)
    (let v (recv
        ((:a x)
            (let y (* x 2))
            (recv ((:b z) (+ y z))))))
    (pprint (list :got v))
    v)

(let w (fork (worker $$)))
(send w (list :a 5))
(send w (list :b 1))
(join w)
```

    t.slight:2:12: a recv can only be in a do that's in tail position, or
    one with no lets; take the message first, with (let m (recv ...))

Expected: it compiles, prints `(got 11)`, and the root's value is
`(ok 11)`. Remove the `(let y ...)` and use `(+ x z)` and it does.

All three shapes of `waitFor` with something after the recv fail the
same way: one clause bound to a name (above), several clauses bound to a
name, and the value dropped (`(recv ...)` as a body form followed by more
forms). Only the case with nothing after the outer recv works, because
`bodies` then holds the clause forms as they are.

### Cause

`compiler/src/split.ts`, `waitFor()`. When there is something after the
recv, every path wraps the clause body in a `do`:

- one clause: `const value = form(r.pos, sym('do', r.pos), ...parts.slice(1))`
  and `letForm(t, value)` (lines 324–328);
- several clauses: the same `value`, passed as the last argument of the
  continuation call, `call(value)`, or put before `call()` as a body form
  (lines 335–344).

The generated function's body then goes through `splitBody`, which finds
the recv inside that `do` and calls `lift()` on it; `lift()` refuses a
`do` with a `let` in it (line 256–259, `throw notTail('do', x)`), since
flattening it would leak its lets into the enclosing scope. The `do` is
there precisely to scope the clause body's lets, so the two parts of the
splitter are at cross purposes.

### Fix

Don't wrap a clause body in a `do` when it has a recv of its own; splice
its forms into the generated clause instead, with the continuation call
around (or after) its last form. Concretely, in `waitFor`:

1. Take the one-clause shortcut only when the clause body has no recv of
   its own: `clauses.length === 1 && !parts.slice(1).some(ownRecv)`. The
   shortcut keeps its `do`, which is right when nothing inside needs
   splitting. A single clause with a nested recv goes through the general
   path below, which makes the continuation a function of its own, so the
   clause body's lets can't reach what comes after.

2. In the general path, build each clause body as a body, not a `do`:
   `init` = the clause's forms but the last, `last` = the last form's
   value (if the last form is a `let`, its value expression, since a
   trailing let's value is the body's value, D42), then

   - value bound (`t !== null`): `[...again(...), ...init, call(last)]`
   - value dropped (`t === null`): `[...again(...), ...init, last, call()]`

   `splitBody` then sees the nested recv where it can handle it: as a
   `let`'s value inside the call's argument (it lifts it out), or as a
   body form followed by the call.

3. The continuation's arguments must not be captured by a `let` in the
   clause body. Today `kArgs` are the plain names (aliased only when a
   pattern binds them), evaluated outside the `do`; spliced in, a clause
   body's `(let n ...)` would shadow an outer `n` that the rest of the
   function expects unchanged. So alias every live name, not just the
   pattern-bound ones: the generated receive function's parameters are
   all `${v} (before ${site})`, `kArgs` are those aliases, and `again()`
   rebinds `v` from its alias at the start of each clause body for every
   live `v` the body uses that its pattern doesn't bind. (Names with
   spaces can't be written by a program, so nothing can shadow them.)
   This also removes the `bound`-based special casing: `alias` no longer
   needs `bound`, and the one-clause shortcut's `back` becomes "rebind
   after the `do` every live name the rest uses that the pattern binds",
   while names the pattern doesn't bind are rebound before the body by
   `again` if the body uses them, and need a rebind before `after` if
   only the rest uses them. Simplest: in the shortcut, rebind before the
   body every live name the body or the rest uses that the pattern
   doesn't bind, and after the `do` every live name the rest uses that
   the pattern does bind (and that isn't `t`). The `@ARGV` carry
   (`argv`) is already an alias; don't alias it twice.

4. A nested recv in a `cond` in a clause body, with something after the
   outer recv, will still be rejected (`lift` refuses a `cond`), as a
   `(let v (cond ... (recv) ...))` is anywhere. That's the existing rule
   ("take the message first"), and the message now points at the user's
   `cond`. Fine to leave; mention it in LANGUAGE.md's recv section if it
   isn't there.

The splitter's comment block at the top of `split.ts` describes the
`(let n (do n))` shape for the one-clause case; update it to say the
clause body is spliced when it has a recv of its own.

### Tests

- Golden `t/NNN-recv-nested-let.slight` with the program above; expected
  output

      (got 11)
      (ok 11)

  Add the two other shapes to the same file or the next number: two
  clauses (`((:a x) (let y (* x 2)) (recv ((:b z) (+ y z)))) ((:c x) x)`,
  send `(:a 5)` then `(:b 1)`), and the dropped-value shape
  (`(recv ((:a x) (let y (* x 2)) (recv ((:b z) (pprint (+ y z))))))`
  followed by `(pprint :after)` and returning `c`). Work the expected
  output out by hand, as the rules say.
- A shadowing test, which passes today and must keep passing, since the
  fix changes how names cross the recv:

  ```lisp
  (defun worker (n)
      (let v (recv ((:a x) (let n 10) (+ n x))))
      (list v n))
  (let w (fork (worker 1)))
  (send w (list :a 5))
  (join w)
  ```

  prints `(ok (15 1))`: the clause's `n` is 10, the rest's `n` is 1.
  And the same with a nested recv after the `(let n 10)`, so the
  continuation path is covered too.
- `compiler/tests/split.test.ts` asserts generated shapes with `show`;
  the aliasing change will move some of them. Update the expectations
  rather than weakening them.
- Run `SLIGHT_GC_STRESS=1` on the new golden tests once by hand: the
  generated functions carry more parameters than before.


## 2. `process.c`: an open socket that nothing can wait on turns a deadlock into a hang

### Symptom

The runtime promises (DESIGN.md, "Deadlock"; LANGUAGE.md:52) to print
`deadlock: the root process is waiting ...` and exit 1 when nothing can
run and nothing can come. With a TCP connection open whose owner isn't
waiting for it, it hangs instead:

```lisp
(defun blocker () (recv (x x)))
(defun holder (q) (recv ((:open c) (join q))))
(defun server (q)
    (let lp (recv ((:open l port) (list l port))))
    (let h (connect :tcp (concat "127.0.0.1:" (cadr lp)) (holder q)))
    (let conn (recv ((:accept l2 conn) conn)))
    (disconnect conn)
    (disconnect (car lp))
    (join h))
(let q (fork (blocker)))
(join (connect :tcp/listen 0 (server q)))
```

Root joins the server, the server joins the holder, the holder took
`(:open c)` and joins the blocker, which waits for a message that never
comes. The listener and the accepted side are closed. Expected:

    deadlock: the root process is waiting for #<pid 3> to end, and nothing else can run
    exit: 1

(pids: root 1, blocker 2, server 3, the listener 4, holder 5, the client
connection 6, the accepted connection 7). Actual: the program never
exits; `timeout 5` kills it.

### Cause

`runtime/process.c`, `idle()` (line ~1000). The deadlock test is

    if (!listening() && !nalarms && !nsockets) return 0;

and `nsockets` counts every open socket. But `socket_fds()` adds a
socket to the `select()` sets only when something can happen to it
without a process running: a listener; a connection that is connecting,
has output waiting, or is readable and whose owner is waiting for it
(`!sent`, `!waiting`, `!eof`, `!closing`); or a lookup. The connection
in the probe is `sent` (its owner took `(:open c)` and never waited
again), so it adds nothing, `max` stays -1, and `wait_for(-1)` becomes
`select(0, ..., NULL)`, which blocks for ever. The same happens with an
accepted connection no one has been handed (`waiting`).

### Fix

Make "a socket that can still do something" mean "a socket `socket_fds`
would add to a set", in one place, and use it for the deadlock test:

1. Factor the predicate out of `socket_fds`: something like
   `static int wants(const rt_device_t *d, int *r, int *w)` giving the
   `r`/`w` it computes now (a lookup counts as wanting its own fd), and
   have `socket_fds` call it.
2. Add `static int sockets_waiting(void)`: 1 if `wants` is true for any
   socket in `sockets`. (Call `bury()` first, as `socket_fds` does, or
   skip the dead ones.)
3. In `idle()`, replace `!nsockets` with `!sockets_waiting()` in the
   first line, and in the virtual-clock branch's
   `if ((listening() || nsockets) && (wait_for(-1) & IO_KEYS))`. Leave
   `events()`'s `!nsockets` as it is: it's only an early-out, and
   `nsockets` is a cheap superset.
4. `wait_for` itself can keep `max`; with the predicate shared, it can
   no longer be called with nothing in the sets and no timeout.

Keep `nsockets` for `events()` and for `new_device`/`close_now`
bookkeeping. Update the comment above `idle()` and the paragraph in
DESIGN.md (around line 679, "never counts as something that can still
happen") to say that a socket counts only while the runtime can wait on
it: an accepted connection no process has been handed, or one whose
owner has its last message and isn't waiting, doesn't.

### Tests

- Golden `t/NNN-socket-deadlock.slight` with the program above and the
  expected output above. Sockets on the loopback already run under the
  virtual clock in `t/173-read-socket-waits.slight`, so this is fine as
  a golden test. Check the pid in the message against what the runtime
  hands out (the order is in the "Symptom" paragraph); don't copy the
  output, work it out.
- Make sure `t/17x` socket tests and `t/186-dns.slight` still pass: a
  lookup in progress must still count as waitable, and so must a
  `closing` socket with output pending.


## 3. (Needs a decision) a killed sleeper's timer keeps the program alive

`end_other()` (process.c:706) leaves a sleeping process's timer in the
heap when the process is killed, as the comment says. On the real clock
the program then runs until the timer fires, for nothing:

```lisp
(let p (fork (sleep 3000)))
(yield ())
(kill p)
(join p)
```

prints `(error killed)` and exits after 3.0 s. D92 chose to keep an
`after` message to a dead process pending until it's due, so the program
"waits for what can still happen"; but a `sleep` timer can deliver
nothing to anyone once the sleeper is gone, so there's nothing that can
still happen.

Proposed: in `end_other`, when `p->state == RT_SLEEPING`, remove its
alarm (scan `alarms` for `pid == p->pid && msg == NULL`, as `unset_alarm`
does, and `remove_alarm` it). Leave `after` alone (D92). Record the
decision in DECISIONS.md either way; if it's rejected, make the comment
in `end_other` say why a sleeper's timer is kept. A golden test can't
observe the difference (the virtual clock jumps), so verify by hand with
`time` on the program above, without `SLIGHT_CLOCK`.

This changes when a program ends, so it's Stevan's call before building.


## 4. Small things, no decision needed

- `fail()` (process.c:1271) can free `d` (a file) or move it to the
  graveyard before it returns, so every caller must return at once
  afterwards. Every caller does today. Put that in the comment above `fail`,
  since nothing else says it.
- `socket_events()` (process.c:1876): when `socket_event` ends the
  current process (`fail` → `rt_end`, reached from `events()` inside
  `rt_preempt`), `free(ready)` and `bury()` are skipped. Either note it
  as accepted (a few words per occurrence, rare), or have `socket_event`
  return whether it ended the caller and let `socket_events` clean up
  first by deferring the `rt_end`: `fail` could set a flag and
  `rt_preempt` end the process after `events()` returns.
- Two UTF-8 lead-byte decoders disagree: `tty.c:103` takes 0xf5–0xff as
  3-byte sequences, `strings.c:265` (`sequence`) rejects them. Expose
  `sequence`'s length rule (or `char_len`) from strings.c in rt.h and
  use it in tty.c.
- Duplicated helpers: `cons_at` (process.c:594, tty.c:132), `hex_value`
  and `is_space` (json.c, sexp.c), `heap_alloc` (json.c:373, sexp.c:484),
  and the out-of-memory `perror`/`exit(2)` idiom eight times in rt.c and
  process.c while `must()` exists in process.c. A `static inline cons_at`
  and `must` in rt.h would cover most of it. In the compiler, `MAX_ARGS`
  (codegen.ts:93, split.ts:44), `isForm` (codegen.ts:481, split.ts:494,
  expand.ts:121 as `headIs`) and `form()` (split.ts:505, expand.ts:132)
  belong in `sexp.ts`.
- Stale comment at codegen.ts:21, "So far (docs/PLAN.md, steps 1-7)".
- `(sexp/parse "=x")` is `(:error (:bad-sexp 1))` while
  `(sexp/parse " =x")` and `(sexp/parse "(=x)")` read a symbol, because
  sexp.c:160 applies the file reader's first-column doc-block rule to a
  string. It's consistent with D164, so leave it, but say so in
  LANGUAGE.md next to `sexp/parse` if it isn't there.
